# OnePlus 9 原生多层显示修复

原生 UIKit / CAMetalLayer / Metal 场景此前在请求 120 fps 时只能完成约 60.5 fps。
公共显示驱动改为双缓冲流水线后，同一程序实测约 116–117 fps。测试程序、着色器、
1125×1260 渲染尺寸和 GPU 的 379 MHz 配置均未改变。

## 原因与实现

程序同时提交 Metal 内容层与 UIKit 界面层。旧路径在一个线程中先合成所有图层，
再等待 DPU 传输完成，CPU 合成与显示传输串行，每帧约 16.5 ms。
`CAMetalLayer nextDrawable` 因缓冲区回收背压等待约 15.8–16 ms；仅把程序改为
异步提交，或优化透明像素处理，均不能解除这个瓶颈。

`MiniIOMobileFramebuffer.cpp` 使用两个内核自有的 BGRA 表面交替合成。
显示工作线程等待实际 DPU 完成时，CPU 可以在另一个表面准备下一帧。
源图层在 CPU 读取完成后释放；自有合成表面在 DPU 传输和可选源图采集完成后才复用。
`SwapWait` 与退出排空同时检查源表面读取和显示传输，失败或超时不会伪造完成。
单层、空白帧及兼容路径切换也先等待正在进行的传输。

## 实机结果（2026-10-25）

各段约 15 秒，先渲染并读回 16×16 已知颜色纹理，BGRA 191/128/64/255 核对通过。
下表统计真实 GPU 完成；显示硬件的独立完成窗口也确认画面持续变化。

| 配置 | 120 fps 轻负载 | 120 fps 重负载 |
| --- | ---: | ---: |
| 同内核关闭流水线的对照 | 60.60 fps | 60.47 fps |
| 同内核开启流水线，带耗时观察器 | 113.93 fps | 112.88 fps |
| 默认配置、无耗时观察器 | 116.26 fps | 117.08 fps |
| 最终设备候选复测 | 116.46 fps | 116.61 fps |

最终设备候选的轻、重负载帧间隔 P95 分别为 8.66、9.21 ms，最大值分别为
19.33、16.98 ms。三段共完成 4,379 帧，无 Metal 错误。60 fps 控制段包含
173.90 ms 启动长帧，全段平均 58.71 fps，其完整稳态显示窗口为 60.02 fps。
设置连续滚动的完整窗口约 119.44–120.04 fps，测试后正常排空并返回加载器。

上述最终设备候选的内核 SHA-256 为
`3e85f828e32ec0eb932cc0bcc71fbc7efd983fe22211ce4fbf48a15343a9043e`。
这是固定 120 Hz 模式，仍有长帧；不代表所有应用稳定锁定 120 fps，
也不是苹果自适应 ProMotion。浏览器和其他第三方应用未在这个候选上重新验收。
源表面读回及硬件完成记录不属于光学拍摄。

## 源码整理与证据范围

合入 `main` 的实现删除了临时 A/B 启动参数、逐帧合成性能输出和 Metal 同步对照开关。
正常功能与上述设备候选一致；整理后的源码重新通过主机回归检查及 ARM64 构建。
主机检查直接运行生产实现，覆盖透明度、裁切、缩放、双缓冲所有权、显示完成顺序、
并发退出和错误保持，相关 C++ 检查启用 ASan/UBSan。

源码提交不等于新运行包验收：完整联合验收的本地包仍为 `2026.10.25-base.4`。
双缓冲设备候选尚未完成对应新内核的整套 DMA 保护、GPU/显示/Wi-Fi 联合及干净运行包验收，
因此没有把 base.4 的验收记录转用于新内核，也没有生成新的正式 ZIP。

私有原始证据分别位于 `local/lemonade/system-promotion-20261025/` 和
`local/lemonade/display-pipeline-20261025/`。流水线对照为 `133848-pipeline0`、
`134050-pipeline1`；默认配置为 `134509-default-ui`，最终设备候选为 `135302-final-ui`。
各次 manifest 绑定内核、System、root 和程序哈希，analysis 绑定日志并去重硬件窗口。
临时 GPU Bench、观察器、自动手势、镜像和原始日志均留在本地，不进入源码提交或日常镜像。
